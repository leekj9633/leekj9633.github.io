### AWS 글로벌 인프라

#### AWS 리전

- 완전한 이중화 및 네트워크 연결로 서버를 안전하게 사용할 수 있다.
- 보통 고객에 대한 근접성, 지연 시간에 따라 리전을 결정한다.
- 가용 영역을 여러 곳 두는데, 이 이유는 서버에 문제가 생길 때 다른 영역의 서버를 바로 사용하기 위함, 즉 안전하게 서버를 계속 구동할 수 있도록 하기 위해서이다.
- 서울 리전에는 **가용 영역**이 여러 개이며, 즉 서울에서는 여러 개의 데이터센터를 쓰고 있다.
- POP: Points of Presence, 리전 외에 각각의 거점을 만들어서 사용자들에게 가까운 거점에 대리점처럼 서버를 세워놓음
    - 네트워크 속도 때문에 리전 외에 작은 대리점을 세워놓는 것, 균등하게 가까운 속도로 제공해야 하기 때문에
- AWS 인프라 기능: 탄력성 및 확장성, 내결함성, 고가용성

### AWS 네트워킹

#### 네트워크 기초

- CIDR은 IP 범위로, 고정된 주소의 개수를 나타낸다.
    - 8자리.8자리.8자리.8자/CIDR ← 형식이기 때문에 앞에서부터 CIDR 값이 작으면 작을 수록 쓸 수 있는 IP 개수가 많아진다. 앞에서부터 고정 자리 계산한다.
- /32는 앞에가 총 32개의 자리이기 때문에 IP 주소 그 자체를 나타낸다.
- 사설 IP는 쓸 수 있는 것이 아래 3가지 주소대역으로 한정되어 있다.
    - 클래스 a, b, c
- OSI 모델, 7계층으로 애플리케이션 - 프레젠테이션 - 세션 - 전송- 네트워크 - 데이터 링크 -물리적 ← 으로 이루어져 있음

#### 아마존 VPC

VPC: 가상 사설 클라우드, 집 안에 여러 자원을 만들 것인데 이를 위한 울타리가 VPC

- 리전을 선택해서 어디에 집을 지을지, 어디에 VPC를 배포할지 선택하는 것
- CIDR 값으로 네트워킹 범위를 알 수 있다. 이후 방을 만들 것인데 이 방은 서브넷이라고 생각하기
- 무한정 VPC를 지을 수 없기 때문에 한 리전별 VPC는 5개만 할당된다. 할당량을 늘리는 요청도 가능.

서브넷: VPC를 분할하는 IP 주소의 범위, 서브넷은 가용영역을 벗어날 수 없다. 단일 가용 영역에 속한다. 퍼블릭과 프라이빗으로 분류된다. 서브넷들은 범위가 중첩될 수 없다.

IP의 사이즈는 바꿀 수 없기 때문에 바꾸고 싶다면 VPC를 새로 생성해야 함. 따라서 여유롭게 CIDR 값 잡기… 가장 큰 블록 크기인 /16으로 지정함

- 1개가 디폴트 값으로 생성 되어 있음
- CIDR는 16으로 가장 많이 IP 주소를 만들 수 있음

!image.png

- 가용 영역에 모두 서브넷을 설치해놓음
- 라우팅 테이블이 있어야 데이터가 왔다갔다 할 수 있음
- 디폴트 vpc는 서브넷 4개가 있고, 공통적으로 하나의 네비게이션(라우팅 테이블, rtb)을 보고 있으며, 인터넷 게이트웨이(네트워크 연결, igw)라는 문을 가지고 있음

VPC 생성 후 서브넷 생성 시, 서브넷들은 같은 가용영역에 두지 않음, 고가용성을 만족시키기 위해서이다.

- 처음 VPC와 그의 서브넷들을 생성하면 인터넷 게이트웨이는 연결되어 있지 않아 내부에서만 통하고 있는 상태이다. (프라이빗 서브넷)

이후 방화벽 (보안그룹) 설정. 게이트웨이 설정 시 제한 두는 것.

- 어떤 프로토콜, 어떤 주소로 들어오는지 보고 제한함.
- 들어오는 아이들은 인바운드, 나가는 아이들은 아웃바운드, 실습에서는 인바운드 규칙 필요
- 응답이 뭔가 안되면 보안그룹을 우선으로 봐야 한다.

아마존 앞에 E가 붙어 있으면 elastic, 즉 탄력적임을 의미. 탄력적 IP 주소는 내가 전용으로 쓰는 IP 주소로, 웹 호스팅처럼 IP 주소가 바뀌면 안 될 때 사용.

#### VPC 네트워킹 구성요소

라우팅 테이블 - 네비게이션

- 주소에 대해 알고 있음, 뭔가 찾아갈 때 얘를 참고해서 찾아감
- 네트워크 간 데이터 트래픽 발생하면 라우팅 테이블이 가리키는 곳으로 감, 경로는 대상 위치와 대상을 지정한다.

퍼블릭 서브넷 - 인터넷이 되는 것, 인터넷 게이트웨이가 필요하다.

VPC로 트래픽 보내기

1. 인터넷 게이트 웨이를 VPC에 연결, 퍼블릭 서브넷
2. 라우팅 테이블을 인터넷 게이트웨이에 연결
3. 인스턴스에 퍼블릭 IP 또는 EIP가 있는지 확인
4. nACL과 보안그룹이 관련 트래픽을 허용하는지 확인 

프라이빗 서브넷과 연결되고 싶다면 퍼블릭 서브넷을 거쳐야 가능. 프라이빗 서브넷이 인터넷과 연결하려면 NAT 게이트웨이가 필요하다. NAT 게이트웨이는 퍼블릭 서브넷에 존재한다.

#### VPC 보안

보안 그룹은 서브넷과 서버 사이에 존재. 인터넷 통신 시 인터넷 게이트웨이를 통해 VPC로 들어와서 서브넷에 들어오기 전에 네트워크 ACL을 거쳐서 들어간다. 네트워크 ACL에서도 허용되는 주소인지 확인한다. 서브넷으로 들어오면 EC2 서버로 들어오기 전에 보안 그룹에서 확인한다. 그리고 서버에 도달할 수 있다. 나갈 때도 마찬가지이다.

**보안 그룹**의 기본은 인바운드에 규칙이 하나도 없다. 즉, 모두 들어오는 트래픽을 차단한다. 아웃바운드 트래픽은 기본적으로 모두 허용한다. 사용자 지정 보안 그룹을 설정할 때는 모든 주소를 허용하지 않고, 실무에서는 특정 주소만 허용해야 한다! **서버**에 제어!

**네트워크 ACL**은 **서브넷**의 문이라고 생각하면 된다. 인터넷 게이트웨이는 VPC의 문이다.

배스천 호스트는 퍼블릭 서브넷에 있고, 프라이빗 서브넷이 필요하거나 호출할 때 괜찮은 요청인지 확인한다.

- 프라이빗 서브넷에 데이터베이스를 두고 퍼블릭 서브넷에서 활동하다가 필요하면 배스천 호스트에 요청

### 컴퓨팅 리소스 - load balancing, auto scaling

트래픽은 일정한 것이 아니다. 서버의 스펙을 정할 때는 보통 사용자가 가장 몰리는 것을 기준으로 하지만, 아예 사용자가 뚝 떨어질 때는 서버가 놀게 된다. → 따라서 ‘탄력성’ 이 필요하게 됨

탄력성: 용량 요구 사항이 변할 때 인프라를 확장하고 축소할 수 있게 만드는 것. 트래픽이 급증할 때는 웹 서버 수를 증대시키고 트래픽이 줄어들면 데이터 베이스의 쓰기 용량을 축소시킨다.

- ELB (엘라스틱 로드 밸런싱): 스케일 아웃(수평적 조정)을 통해 서버를 늘리거나 스케일 업(수직적 조정)을 통해 서버의 사양을 늘려서 탄력성을 실현할 수 있다.
    - 스케일 업(수직적 조정)은 서버를 중지시켜야 새로운 장소에 자리를 잡아서 사양을 키워야 한다.
    - 스케일 아웃(수평적 조정)은 기존에 일하고 있던 서버들도 일을 하고 새 서버들도 추가할 수 있어 서비스 중지를 시키지 않아도 된다.
- 오토 스케일링: 자동으로 서버의 수를 늘리거나 줄이는 것.
    - 사용자들의 추이에 따라 변경하는 ‘동적’ 스케일링, 내가 예상치 못할 때도 잘 대응.
        - 단순 조정
        - 단계 조정: CPU 사용량이 특정 값일 때 서버 추가해줘.
        - 대상 추적 조정: 특정 지표에 대한 목표 값. CPU 사용량을 특정 지표로 맞춰 그것으로 유지되도록.
    - ‘예약’, 특정 시점에 늘리는 것. 수강신청 기간이나 티켓팅에는 보지 않아도 사용자가 많이 몰리니 기간을 알면 사용할 수 있는 옵션.
    - ‘예측’, 머신러닝 가미. 과거의 데이터를 보고 패턴을 파악해서 대응.
    - 오토 스케일링은 그룹으로 만들어져 활동한다. 오토 스케일링의 그룹 크기는 사용자가 원하는 용량으로 설정한 인스턴스 수에 따라 달라진다. 최대 크기와 최소 크기를 조정할 수 있다.
    - AMI와 인스턴스 유형, 보안 그룹 등으로 시작 구성 → 오토 스케일링 그룹 설정 → when 설정
    - 프로세스: CloudWatch로 모니터링 하고 Load Balancing이 자동 조정하여 EC2에 반영한다.

### AWS Stroage

#### Strage란?

서버에서 데이터를 가지고 있을 수도 있지만, 중요한 파일은 별도의 저장소에 저장한다. 

스토리지 서버라는 것도 가상화를 한다. 스토리지의 형식은 블록 스토리지 (파일을 여러 칸에 나눠서 저장하고 그것을 수정할 때 수정할 칸에 가서 수정하기 때문에 컴퓨터가 이해하기 좋아서 속도가 빠르다), 파일 스토리지 (탐색기, 사람이 보기 편함, 계층 구조), 오브젝트 스토리지 (구글 드라이브 형태, 다양한 컨텐츠 자유롭게 올려서 읽을 수 있고 사람이 보기 편함)

- EBS, EFS, S3가 스토리지 서비스가 된다.

#### Amazon EBS - elastic block storage

루트 볼륨과 데이터 볼륨 두 개로 나누어진다. 루트 볼륨의 인스턴스 스토어는 EC2에서 8기가로 지정하는 그것이고, EBS는 내 데이터 저장하는 것이다.

- 인스턴스 스토어: 서버 만들어질 때 만들어짐. 인스턴스 중지, 종료될 때 인스턴스 스토어 손실되어 중요 데이터는 이곳에 넣으면 안 됨
- 블록 스토리지(EBS): 블록 수준 스토리지, 저장 주머니 생성하는 것으로 보면 된다.
    - EBS의 특성: 컴퓨터에 연결된 저장소처럼 보이지만 완전히 다른 곳에 있는 것이라고 보면 된다. SSD, HDD에 저장할 수 있고 선택할 수 있다.
    - 기능: 스냅샷, 암호화, 탄력성
    - 선택 기준: 용량, 입출력 속도 (IOPS),  스냅샷, 데이터 전송

#### Amazon EFS - elastic file storage

파일 형태로 저장한다.

EBS는 EC2와 1:1로 매핑된다. 외장하드처럼. / EFS는 여러 EC2들이 공유해서 쓸 수 있다. 공유 저장소처럼.

NFS 프로토콜로 인해 리눅스 기반이다. EC2가 리눅스 기반이여야 공유해서 EFS를 사용할 수 있다.

윈도우즈 용은 Amazon FSx를 사용하면 된다. 프로토콜이 SMB를 사용한다. 하는 역할은 EFS와 같다.

#### Amazon S3 - simple storage service

- 객체 스토리지
    - 비정형 데이터 무제한으로 저장 가능
    - 대표적인 서버리스 서비스, 저장소 사이즈 지정하지 않아도 됨
- 버킷이라는 형태를 가지고 있음, 무제한으로 저장 가능, HTTP로 접근 가능, 내구성이 좋음
- 장점
    - 스탠다드 형은 내구성이 좋음, 10만개의 파일을 10000년 저장해도 1개 파일을 손실할까 말까 정도임
    - 언제든지 데이터에 액세스할 수 있는 가용성이 좋고, 확장성과 보안, 성능이 좋음
- 삼중복제를 해놓아서 데이터는 거의 무조건 유지된다고 보면 됨
- 보통은 애플리케이션 자산 저장, 정적 웹 호스팅, 백업 및 재해 복구, 빅데이터를 위한 스테이징 영역 등을 사용할 때 S3 사용한다.
- 데이터 업로드 방법: AWS 리전에 버킷 생성 → 원하는 만큼 객체 버킷에 업로드
- 버전 관리
    - 파일을 덮어쓰거나 삭제하는 걸 방지한다. 잘못 덮어써도 이전 데이터로 원상 복구 가능.
    - 기본은 버전 관리하지 않지만, 옵션에서 선택하면 가능

### AWS Security

#### 공동 책임 모델

- AWS를 사용하는 사용자와 AWS는 각자의 책임이 있다. 사용자는 클라우드에서의 보안에 대한 책임이 있고, AWS는 클라우드 자체의 보안에 대한 책임이 있다.

#### IAM - identity and Access Management

- 계정 관리 및 로그인 설정, 서버 관리자가 관리하는 사용자들을 관리
- IAM에서 리소스 관리를 하는데, AWS에서 무료로 제공하는 계정
- 구성 요소: 사용자, 그룹, 정책, 역할
    - 사용자: 계정 ID, 사용자 이름, 암호로 로그인하게 됨
        - MFA: 보안을 향상 시켜서 고유한 인증 코드를 제공해야 AWS 서비스에 액세스 가능
    - 권한 부여: 각 IAM 사용자들에게 허용되는 작업에 대한 권한을 부여함
        - 최소 권한 원칙(사용자가 할 수 있는 작업을 결정하여 이 작업만 수행할 수 있게 하는 정책)을 따라야 함
    - 정책: 세분화된 액세스 제어가 가능한 권한을 정의하는 문서
        - 유형: 자격 증명 기반 정책 (IAM 개체에 연결, 개체가 수행 가능한/불가능한 작업 지정), 리소스 기반 정책 (EC2와 S3를 연결할 때 사용하는 등 모든 자원에 대해 접근하는 것은 정책 필요)
        - 명시적 허용: 사용자에게 특정 서비스에 대한 액세스 권한 부여
        - 명시적 거부: 특정 서비스 제외하고 다른 AWS 작업 또는 리소스 사용 불가
            - 허용문보다 우선 적용
    - 그룹: 여러 사용자에게 같은 권한을 주기 위해 묶어놓음, 그룹 중첩 불가
    - 역할: role이 아니라, 임시적으로 특정 작업을 할 때 사용 - 임시 보안 자격 증명

#### AWS 계정 보안

- 계정 루트 사용자보다는 IAM 사용자로 생성해서 사용해라.
- MFA 활성화 - 구글 authenticator 등의 애플리케이션을 사용해서 보안 업!
- AWS CloudTrail로 IAM 사용자들의 활동을 추적하며 모니터링
- 결제 보고서를 활성화하여 분석하기
- IAM 유저든 아니든, AWS의 액세스 키를 파일에 올리고 .gitignore에 올려야 깃허브에 올라가지 않는다.
- KMS - key management service: 키 제어하고 관리하는 서비스
- AWS Cognito: 앱 인증서비스, 카카오톡으로 로그인 같은 것임
- AWS Shield: DDoS 방어를 위한 관리형 서비스

#### AWS Organizations

- 루트 계정이 있고 OU(Organization Unit)이 각각 있고, 유닛에 속한 계정은 유닛의 권한을 각각 가지게 된다.
- 정책 기반 계정 관리, 그룹 기반 계정 관리, 계정 관리를 자동화하는 애플리케이션 프로그램 인터페이스, 통합 결제 등에 대한 이점이 존재한다.
- 서비스 제어 정책을 사용하여 관리한다.

#### AWS의 데이터 보안

- 데이터를 암호화하는 것을 권장한다.
- https를 사용하는 것이 보통인데 이때는 인증서가 필요하고 인증서를 편하게 관리하기 위해서는 AWS Certificate Manager 라는 서비스를 사용하면 가능하다.
